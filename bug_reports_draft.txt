БАГ-РЕПОРТ №1
========================================================================
Заголовок: Некорректный id у спойлера фильтра без привязанного поля формы
(встречается на нескольких страницах)

Страницы:
- https://gsz.gov.by/registration/vacancy-search/
  (спойлер "Дополнительные параметры")
- https://gsz.gov.by/registration/gpd/public-works/
  (спойлер "Предмет гражданско-правового договора")

Приоритет: Низкий
Серьезность: Косметическая / технический долг (на функциональность
пользователя не влияет)

Шаги воспроизведения:
1. Открыть любую из страниц выше
2. Открыть DevTools -> Elements
3. Найти блок фильтра, указанный в скобках для этой страницы
4. Посмотреть атрибуты заголовка спойлера (div.card-header)

Фактический результат:
Атрибуты заголовка спойлера на обеих страницах одинаково сломаны:
  id="-header"
  data-target="#-collapse"
  aria-controls="-collapse"
То есть id состоит только из суффикса "-header"/"-collapse" без префикса
с именем поля. Для сравнения, у соседних фильтров на тех же страницах:
  id="id_area-header" / data-target="#id_area-collapse" (Сфера деятельности)
  id="id_business_entity-header" / data-target="#id_business_entity-collapse" (Наниматель)
  id="wage_rate-header" (Ставка, vacancy-search)
  id="id_search_period-header" (Период публикации, vacancy-search)
А у "Дополнительные параметры" / "Предмет ГПД" префикс с именем поля
отсутствует.

То, что баг идентичен (один и тот же "-header"/"-collapse") сразу на двух
разных страницах с разным набором полей, говорит о том, что это не
случайная опечатка в одном шаблоне, а системная проблема в общем
макросе/инклюде, который рендерит спойлер фильтра, когда ему не передают
имя поля (используется для группы чекбоксов / нескольких полей без
единого field name).

Ожидаемый результат:
id и data-target должны строиться по тому же паттерну, что и у остальных
фильтров на странице, например:
  id="id_type_gpd-header" / data-target="#id_type_gpd-collapse" (ГПД)
  id="id_additional_params-header" / data-target="#id_additional_params-collapse" (vacancy-search)

Влияние:
Раскрытие спойлера по клику работает корректно (id header и collapse
ссылаются друг на друга последовательно), но:
- нарушена консистентность разметки между однотипными фильтрами;
- усложняет автоматизацию/тестирование и любую стороннюю интеграцию,
  которая ожидает предсказуемый паттерн id вида "id_<field_name>-header";
- при появлении третьего такого "безымянного" спойлера на любой другой
  странице оба блока будут ссылаться на один и тот же "#-collapse",
  что может привести к одновременному раскрытию/закрытию обоих блоков
  сразу (нужно перепроверить, если такая ситуация когда-либо возникнет
  на одной странице).

Предполагаемая причина:
Общий шаблон/макрос генерации спойлера ожидает на входе имя поля
(field name) для построения id, но для группы полей без единого field
name (чекбоксы "Предмет ГПД", группа "Дополнительные параметры") имя не
передается, и в id попадает только статичный суффикс.

БАГ-РЕПОРТ №2
========================================================================
Заголовок: У select2-selection__rendered нулевая высота (height: 0px) —
встречается на всех проверенных страницах с фильтрами Select2

Страницы (проверено и воспроизведено на всех):
- https://gsz.gov.by/registration/vacancy-search/
- https://gsz.gov.by/registration/temporary-employment/public-works/
- https://gsz.gov.by/registration/gpd/public-works/
- https://gsz.gov.by/registration/future-vacancy/future-works/

Приоритет: Низкий
Серьезность: Косметическая / влияет на автоматизацию и доступность
(на визуальное поведение для пользователя не влияет)

Шаги воспроизведения:
1. Открыть любую из страниц выше
2. Открыть DevTools -> Elements
3. Выбрать любой select2-виджет на странице (например, фильтр "Область",
   "Наниматель", "Сфера деятельности" — как single-select, так и
   multiple-select варианты)
4. Посмотреть computed-стили / getBoundingClientRect() элемента
   span.select2-selection__rendered

Фактический результат:
Во всех проверенных select2-виджетах на всех 4 страницах
getBoundingClientRect() элемента span.select2-selection__rendered дает
height: 0 и width: 0 (при этом visibility: visible, display: block, то
есть элемент не считается скрытым по обычным CSS-критериям).

На странице vacancy-search/temporary-employment/public-works это
происходит из-за инлайн-стиля прямо на странице:

  .select2-container--default .select2-selection--single
  .select2-selection__rendered {
    line-height: 34px !important;
    color: #495057 !important;
    font-size: 1rem !important;
    padding-left: 0 !important;
  }

В этом блоке не задан height, в отличие от родительского
.select2-selection--single, для которого явно задано height: 48px
!important. Из-за этого боксы вложенного элемента и родителя расходятся.
На остальных страницах (gpd, future-works) воспроизводится тот же эффект
для multiple-select виджетов (select2-selection--multiple) — судя по
всему, общий стиль/тема select2 на сайте в принципе не задает height
вложенному __rendered, и проявляется он везде одинаково, а не только там,
где есть локальный <style> override.

Ожидаемый результат:
Боковой бокс span.select2-selection__rendered должен иметь ненулевую
высоту (либо наследовать height: 100% / auto от родителя), чтобы
соответствовать реальной видимой области элемента, — во всех select2
виджетах на сайте, а не только на отдельных страницах.

Влияние:
Визуально для пользователя текст в поле виден (за счет line-height и
overflow: visible у родителя), сам выпадающий список открывается по клику
без проблем. Но:
- элемент с нулевым bounding box некорректно обрабатывается инструментами,
  ориентирующимися на геометрию (автотесты Playwright/Selenium, проверки
  доступности, скринридеры) — такие инструменты могут считать элемент
  невидимым/некликабельным;
- так как баг системный (воспроизводится на 4 из 4 проверенных страниц),
  чинить его правдоподобнее в общей CSS-теме select2/bootstrap4, а не
  точечно на одной странице.

Предполагаемая причина:
Общая CSS-тема select2-bootstrap4, используемая на сайте, не задает
height для .select2-selection__rendered, рассчитывая, что высота
наследуется от родителя за счет line-height/padding, но в некоторых
браузерах/конфигурациях computed height вложенного элемента остается 0.

Заголовок: Дублирующийся id="logo-gsz" у двух разных <img> в шапке сайта

Страницы (проверено и воспроизведено на всех):

- https://gsz.gov.by/registration/temporary-employment/public-works/
- https://gsz.gov.by/registration/gpd/public-works/
- https://gsz.gov.by/registration/future-vacancy/future-works/
- https://gsz.gov.by/registration/training-course/public/list/

Приоритет: Низкий
Серьезность: Нарушение валидности HTML (на видимое поведение для
пользователя не влияет)

Шаги воспроизведения:
1. Открыть любую из страниц выше
2. Открыть DevTools -> Elements -> Ctrl+F по "id=\"logo-gsz\""
   (или document.querySelectorAll('#logo-gsz') в консоли)

Фактический результат:
На каждой странице найдено 2 разных <img> с одинаковым id="logo-gsz",
оба лежат внутри <picture> (вероятно, переключение лого по теме/цвету
фона через <picture>/<source> или JS):
  <img src=".../logo-white....png" ... id="logo-gsz" class="logo-white">
  <img src=".../logo.....svg" ... id="logo-gsz" class="logo-default">

следует использовать общий class, а не дублирующийся id, либо разные id
(например "logo-gsz-white" / "logo-gsz-default").

- невалидный HTML;
- document.getElementById('logo-gsz') / CSS-селектор #logo-gsz всегда
  вернет только первый элемент, второй становится недостижим через id
  (если где-то в JS/CSS адресация идет по этому id, это может быть скрытым
  источником багов с "неправильной" картинкой логотипа);
- затрудняет автоматизацию/тестирование, ориентирующуюся на уникальность id.

Предполагаемая причина:
Общий header-компонент (используется на всех страницах сайта) при верстке
переключения логотипа light/dark скопировал id вместо использования
общего class.

БАГ-РЕПОРТ №4 (информационный, не блокер)
========================================================================
Заголовок: CSP-директива frame-ancestors задается через <meta>-тег и
поэтому полностью игнорируется браузером

Страницы (проверено и воспроизведено на всех):
- https://gsz.gov.by/registration/vacancy-search/
- https://gsz.gov.by/registration/temporary-employment/public-works/
- https://gsz.gov.by/registration/gpd/public-works/
- https://gsz.gov.by/registration/future-vacancy/future-works/
- https://gsz.gov.by/registration/training-course/public/list/

Приоритет: Низкий (проверено: реальная защита есть через отдельный
заголовок, см. ниже)
Серьезность: Мертвый код / избыточная директива, без реального влияния
на безопасность

Шаги воспроизведения:
1. Открыть любую из страниц выше
2. Открыть DevTools -> Console

Фактический результат:
В консоли на каждой странице выводится предупреждение/ошибка браузера:
  "The Content Security Policy directive 'frame-ancestors' is ignored
  when delivered via a <meta> element."
Это означает, что директива frame-ancestors задана через
<meta http-equiv="Content-Security-Policy" ...> в HTML, а не через HTTP-
заголовок ответа. По спецификации CSP, frame-ancestors поддерживается
ТОЛЬКО при передаче через HTTP-заголовок (Content-Security-Policy в
ответе сервера) и полностью игнорируется, если задана через <meta>.

Ожидаемый результат:
Если задача директивы — ограничить встраивание страницы в <iframe> на
сторонних доменах (защита от clickjacking), ее нужно отправлять как
настоящий HTTP-заголовок Content-Security-Policy (или дублировать через
X-Frame-Options для старых браузеров), а не через <meta> в HTML.

Влияние:
Проверено через `curl -I https://gsz.gov.by/registration/vacancy-search/` —
сервер реально отдает заголовок `X-Frame-Options: SAMEORIGIN`, то есть
базовая защита от clickjacking на сайте есть и работает независимо от
сломанной meta-директивы. Таким образом, сама meta-директива
frame-ancestors — просто мертвый/бесполезный код, реального риска для
безопасности на момент проверки нет. Имеет смысл либо убрать ее из
<meta>, либо (что чище) перенести в реальный HTTP-заголовок
Content-Security-Policy наравне с X-Frame-Options, чтобы не плодить
ложные предупреждения в консоли и не вводить в заблуждение при будущих
security-ревью.

Предполагаемая причина:
При настройке CSP политику добавили через <meta>-тег в шаблон (проще
конфигурировать на уровне фронтенда), не учтя, что эта директива
по спецификации работает только через HTTP-заголовок.

БАГ-РЕПОРТ №5
========================================================================
Заголовок: Спойлеры фильтров "Регион обучения" и "Период обучения"
полностью недоступны с клавиатуры

Страница:
- https://gsz.gov.by/registration/training-course/public/list/
  (вероятно, тот же общий компонент filter-block, что и в баг-репорте №1,
  поэтому проблема может воспроизводиться и на других страницах с такими
  же спойлерами — не перепроверялось целенаправленно за рамками этой
  страницы)

Приоритет: Средний
Серьезность: Нарушение доступности (WCAG 2.1.1 Keyboard) — фильтры
региона и периода обучения нельзя открыть, не используя мышь/тач

Шаги воспроизведения:
1. Открыть страницу выше
2. Не используя мышь, последовательно нажимать Tab от начала страницы
3. Либо в DevTools -> Console выполнить:
   document.querySelector('#id_region-header').tabIndex
   document.querySelector('#start-date-header').tabIndex

Фактический результат:
Оба заголовка спойлеров — это <div class="card-header" ... data-toggle=
"collapse" ...> без role="button" и без tabindex. Свойство tabIndex у
обоих элементов равно -1, то есть они принципиально не получают фокус
по Tab и не входят в последовательность обхода клавиатурой. Раскрытие
спойлера реализовано только через mouse/touch click-обработчик Bootstrap
collapse. При этом сами div корректно несут атрибуты aria-expanded/
aria-controls — то есть для screen reader разметка частично подготовлена,
но фактическая фокусируемость элемента отсутствует, поэтому ассистивные
технологии до него вообще не доберутся по Tab.

Ожидаемый результат:
Интерактивный заголовок спойлера должен быть либо реальным <button>,
либо иметь role="button" + tabindex="0" + обработчик нажатия Enter/Space
(стандартный паттерн для кастомных collapse-тоглов), чтобы пользователь,
не использующий мышь, мог дойти до него по Tab и раскрыть скрытые поля
"Регион обучения" / "Период обучения".

Влияние:
- пользователи, работающие только с клавиатуры (моторные нарушения,
  переключатели/switch-access), и пользователи скринридеров не могут
  раскрыть и заполнить эти два фильтра вообще — то есть часть функционала
  поиска курсов обучения для них полностью недостижима;
- сами поля фильтров (select#id_region, input#id_period_start,
  checkbox#id_start_when_full) физически существуют в DOM и валидны, но
  пока родительский collapse-блок не раскрыт мышью, до них нельзя дойти
  по Tab, так как display:none убирает их из последовательности обхода.

Предполагаемая причина:
Тот же общий шаблон/макрос filter-block, что фигурирует в баг-репорте №1,
рендерит заголовок спойлера как обычный <div> с data-toggle="collapse"
для Bootstrap JS, не добавляя role/tabindex/keydown-обработчик, нужные
для доступности кастомного интерактивного контрола.

БАГ-РЕПОРТ №6
========================================================================
Заголовок: Ссылки "Контактные данные службы занятости" на карточках
курсов обучения открываются в новой вкладке без rel="noopener"

Страница:
- https://gsz.gov.by/registration/training-course/public/list/
  (на странице выдачи 10 карточек курсов обучения — все 10 ссылок
  "Контактные данные службы занятости" воспроизводят проблему одинаково)

Приоритет: Низкий
Серьезность: Best-practice безопасности/производительности (tab-nabbing),
риск снижен тем, что ссылка ведет на тот же домен gsz.gov.by

Шаги воспроизведения:
1. Открыть страницу выше
2. Открыть DevTools -> Elements, найти на любой карточке курса ссылку
   "Контактные данные службы занятости"
3. Посмотреть атрибуты target и rel у этого <a>

Фактический результат:
  <a href="/directory/information/employment-departments/?region=...&district="
     target="_blank" class="btn btn-outline-primary" title="...">
    Контактные данные службы занятости
  </a>
Атрибут rel отсутствует. При target="_blank" без rel="noopener"
(или "noreferrer") открытая страница получает доступ к window.opener
исходной вкладки и теоретически может переопределить ее location
("reverse tabnabbing"), а сам открытый процесс/вкладка не изолируется от
родительской (доп. нагрузка на event loop родительской страницы).

Ожидаемый результат:
У всех ссылок с target="_blank" должен быть атрибут rel="noopener"
(или rel="noopener noreferrer", если переход потенциально может вести и
на внешний домен).

Влияние:
Поскольку ссылка ведет на тот же домен (gsz.gov.by), практический риск
reverse tabnabbing невысокий, но это все равно нарушение текущих
рекомендаций безопасности (OWASP, Lighthouse best practices). Также
стоит обратить внимание, что часть других target="_blank" ссылок на
сайте (например, в подвале — ссылка на mintrud.gov.by, Яндекс.Метрика)
ведет на внешние домены и страдает той же проблемой уже с более высоким
риском, но это общий футер сайта, а не специфика страницы обучения.

Предполагаемая причина:
В шаблоне карточки курса обучения у ссылки задан target="_blank" без
сопутствующего rel="noopener", вероятно по тому же паттерну, что и у
футера сайта.

БАГ-РЕПОРТ №7
========================================================================
Заголовок: Нарушена иерархия заголовков — после <h1> сразу идут <h4>,
без <h2>/<h3>

Страница:
- https://gsz.gov.by/registration/training-course/public/list/

Приоритет: Низкий
Серьезность: Нарушение доступности/SEO (WCAG 1.3.1, 2.4.6) — не блокер,
видимое поведение для пользователя не страдает

Шаги воспроизведения:
1. Открыть страницу выше
2. В DevTools -> Console выполнить:
   [...document.querySelectorAll('h1,h2,h3,h4,h5,h6')].map(h => h.tagName)

Фактический результат:
На странице ровно один <h1> ("Обучение") и далее 13 элементов <h4>
("Обучение безработных и граждан...", "Регион обучения", "Период
обучения", заголовки каждой из 10 карточек курсов обучения) — уровни
<h2> и <h3> на странице отсутствуют полностью (их количество — 0).

Ожидаемый результат:
Структура заголовков должна идти по возрастанию без пропуска уровней,
например: <h1> "Обучение" -> <h2> на смысловые блоки (вступительный
текст, панель фильтров, список результатов) -> <h3> на заголовки
отдельных карточек курсов, либо хотя бы не пропускать сразу 3 уровня
(h1 -> h4).

Влияние:
- пользователи скринридеров обычно навигируют по странице "от заголовка
  к заголовку" и ориентируются по уровню вложенности — резкий скачок с
  h1 на h4 ломает ожидаемую семантическую структуру документа;
- так же ухудшает SEO-разметку структуры страницы (заголовки используются
